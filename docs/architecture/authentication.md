# Individual accounts (ACC-02/03)

The server-only Supabase SSR client uses HttpOnly, SameSite=Lax cookies. Production cookies are Secure (loopback local Supabase development is exempt). Proxy refreshes cookies and disables response caching. Protected layouts, password changes and access actions call Auth getUser then read the live active membership under RLS. Never authorize with getSession or JWT user metadata. Missing configuration permits only the existing data-free construction preview; it provides no data client or mutation access.

No self-registration is provided; local Auth signup is disabled globally with `[auth].enable_signup = false`. Keep `[auth.email].enable_signup` and `[auth.sms].enable_signup` true: these provider switches also govern existing-account password sign-in despite their names. The CLI disables phone/password login unless an SMS provider is enabled. Local config uses synthetic Twilio identifiers and a test OTP for the synthetic test identity; set SUPABASE_AUTH_SMS_TWILIO_AUTH_TOKEN=synthetic-local-only before local startup (CI supplies it). This placeholder cannot deliver SMS, and password login does not send SMS. Never copy synthetic provider values or test OTPs into hosted settings. Hosted phone authentication must be enabled separately. See [CLI provider validation](https://github.com/supabase/cli/blob/v2.122.0/apps/cli-go/pkg/config/config.go) and [password authentication](https://supabase.com/docs/guides/auth/passwords). Trusted provisioning creates each identity and membership; phone-login users need an Auth phone identifier and an email for recovery. Owners alone have the is_owner capability, constrained to the owner/owner_doctor base roles. ACC-04 lets an existing owner assign clinic roles and extra list tags through an audited RPC; self-role changes and Platform Admin assignment are denied. Role changes serialize per organisation and recheck the actor after locking, preventing concurrent owners from removing each other’s authority. Tags do not grant access; ACC-05/06 will define detailed presets and permissions. No service-role key is used by the application. Detailed navigation permissions are not implemented yet: authenticated rail destinations default to none until ACC-06, and login opens the data-free Calendar. Future protected screens must check their own area permission in addition to this account gate.

Account access changes validate zod input, check the live owner capability, and invoke set_login_access. The RPC rechecks ownership, serializes on the organisation, checks tenant/soft-delete constraints, refuses self changes, updates and appends an immutable audit entry atomically. There are no direct client write grants. Disabling login immediately makes auth_org_id return null and the protected application refuses the existing session. Auth can still issue an identity session; that session cannot enter the app or access tenant tables. Password resets never enable a disabled membership.

Password changes belong to Supabase Auth, which owns password hashing and auth audit events. They cannot share a Postgres transaction with application audit; do not duplicate passwords or Auth tokens in application audit. Success revokes other refresh sessions; existing access tokens may remain valid until expiry. Login-enable changes additionally cut off database access immediately through live membership/RLS checks. Provider errors and credentials are never logged or returned.

Recovery requests return the same message for known/unknown emails and provider errors. Configure Auth rate limits and approved email delivery before live use. Owner Set New Password sends the standard recovery link: the account holder chooses a password, and the owner never sees it. This is a deliberate security decision pending clinic review. Recovery links use the fixed AUTH_SITE_URL, not an untrusted Host header or return URL. Configure the recovery email template as documented below; only recovery token hashes are accepted by the callback, with no arbitrary next redirect. Links are single-use and expire in Auth. Configure short JWT expiry and secure password change/reauthentication in the hosted project.

Mobile access is best effort via the User-Agent on every protected request and password action. It detects normal Android/iOS/tablet strings. Desktop-mode browsers, changed User-Agent headers and some iPads can evade it; it is not a device attestation boundary. Desktop access remains available. Owners cannot change their own login/mobile switches.

## Provisioning and recovery setup

Use local Supabase and synthetic accounts for development. Hosted projects must be owner-created in Mumbai. Set NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY and AUTH_SITE_URL in the environment. Never use service-role credentials in a browser. Trusted SQL/admin provisioning must associate exactly one membership with each Auth identity and set the first owner's is_owner = true, base_role = 'owner' and login_enabled = true; no public provisioning endpoint exists. Team/person creation belongs to the later settings screens.

Set Auth site URL to AUTH_SITE_URL, allow the exact /auth/confirm callback, disable public registration, require at least 12-character passwords, and configure approved email delivery. Change the Reset Password email link to `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery`. Local Supabase uses supabase/templates/recovery.html. Never use real patient records or real clinic accounts for tests.
